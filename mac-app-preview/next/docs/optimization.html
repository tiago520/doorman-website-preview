Find repeated work, test one supported change, and inspect the result before counting its contribution.

Start with a recorded successful task.

Choose one recurring workflow and keep its current successful result as the reference. You need a configured gateway, an appropriate traffic key, request visibility and permission to change the relevant setting. Provider usage from comparison requests may be billable.

  1. Match a real request to its client, time and model.
  2. Inspect the grouped task for repeated input, tool results and retries.
  3. Choose one optimization that addresses the observed waste.

Match the mechanism to the waste.

MechanismGood fitVerify
Model routingRoutine work has sufficient quality evidence for a cheaper supported model.Served model, required capabilities, result quality and retries.
Provider cache controlsRepeated supported prompt segments are not already cache-enabled by the client.Actual provider cache behavior and incremental attributable saving.
Exact embedding reuseThe same model, input, dimensions and encoding are requested again.A repeated result is reused within its organization; model changes remain distinct.
Tool-schema compactionRepeated eligible tool definitions consume context.Required tool semantics remain intact and the recorded contribution is present.
Tool-output compressionVerbose tool results are repeatedly included in later turns.Monitor opportunity first, then compare an eligible applied request.

Try compression in monitor mode.

A gateway operator controls the tool-output rollout. The setting is server configuration, not a command for an end user’s client shell.

# Measure eligible compression opportunities; preserve the request body.
TOOL_OUTPUT_COMPRESSION=monitor

# Apply the supported transform after an authorized review.
TOOL_OUTPUT_COMPRESSION=true

# Keep compression disabled.
TOOL_OUTPUT_COMPRESSION=off

Choose one value in the gateway’s deployment configuration. Monitor mode measures potential token reduction but reports no applied savings. Apply mode transforms eligible content; explicit passthrough and SUBS paths remain excluded, and transform failures preserve the original body.

Compare tool names, required fields and task usefulness using representative inputs. Changing a flag alone does not establish quality or savings.

Verify exact embedding reuse.

Supported OpenAI-style embedding requests use POST /openai/v1/embeddings. The cache identity includes organization, model, input, dimensions and encoding format. In a mixed batch, only misses need a provider request.

  1. Use an embedding model and request shape supported by your provider configuration.
  2. Repeat a harmless test input with the same model and dimensions.
  3. Inspect cache-hit telemetry and recorded usage under the same organization.
  4. Change the input or dimensions and verify that a distinct result is requested.

A cache failure falls back to the provider. Do not infer a cache hit solely from response speed, and do not substitute a cheaper embedding model without rebuilding or validating vector compatibility.

Count the contribution that was delivered.

Refresh the request record and Savings view after the test. Compare the result with the baseline task and read the contribution’s scope. Existing provider cache discounts, Doorman cache injection and a model-routing delta are different amounts.

Qualifying retries and applicable report adjustments can reduce a saving. A monitor estimate or eligibility flag is not a delivered reduction. The current batch-arbitrage submission/poll/retrieval lifecycle is deferred; batch eligibility alone does not create an asynchronous job.
