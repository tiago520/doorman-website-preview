Prepare a receiver and an owner.

You need an organization administrator, an approved public HTTPS receiver and a place to store its signing secret. Choose the few events your team will act on, and name the person or system responsible for each. A webhook delivers an event; your receiver decides how to create a ticket or notification.

Start with a test receiver

Keep the first destination away from a paging workflow. The console’s Test action makes a real outbound delivery in your own environment. The public sample console only demonstrates the interface.

Register one destination.

  1. Open Organization → Integrations in your own console and choose New webhook.
  2. Enter a descriptive name and the receiver’s approved HTTPS URL. Select the events you need.
  3. Capture the one-time signing secret from the supported admin creation workflow and store it on the receiver. If your console cannot display it, use the authenticated admin API workflow.
  4. Keep the endpoint private to your operators: some destination URLs contain credentials.

The create endpoint is POST /api/admin/webhooks with a body shaped like this; use your authenticated administrator session and CSRF protection.

{
  "name": "Pilot governance receiver",
  "url": "https://events.example.com/doorman",
  "events": ["tool_approval_required"]
}

Registration rejects non-HTTPS and private/loopback/metadata destinations. Select supported events from the environment rather than treating an integration name as proof a connection exists.

Verify the original request bytes.

Doorman-Signature: t=<unixSeconds>,v1=<hexDigest>

hexDigest = HMAC-SHA256(
  webhookSigningSecret,
  "<unixSeconds>.<raw JSON body>"
)
  1. Read the raw request body before parsing or reserializing JSON.
  2. Parse the timestamp and v1 signature. Compute the digest using the full whsec_* secret.
  3. Compare digests in constant time and reject a missing, invalid or stale signature. The default verification tolerance is 300 seconds.
  4. Only then parse and dispatch the event. Keep clocks synchronized and make downstream handling safe to retry.

Older hooks may have no signing secret. Rotate the secret through the supported admin workflow before requiring signed delivery; do not accept an unsigned request as a successful verification.

Check delivery at both ends.

Use Test on the webhook row. On the receiver, confirm the signature was accepted and the event was processed once. In Doorman, inspect the reported delivery result and destination status. A successful HTTP request with a rejected downstream job is not the complete result.

SignatureRaw-body digest and timestamp validate.

Fix the failing layer.

For a URL rejection, use an approved reachable HTTPS receiver. For a signature failure, check raw-body handling, clock drift and the current secret. For a delivery timeout or non-success response, inspect the receiver before retrying. Coordinate secret rotation at both ends; new signing secrets are shown once.

Pause the noisy destination through the supported administration path while repairing it. Keep the underlying governance record available in the audit or approval view.

Make the event actionable.

Route approval events to a reviewer, budget events to the allowance owner, and security events to the appropriate investigation workflow. Include the record identifier and console destination; avoid copying secrets or full prompt content into general team channels.
