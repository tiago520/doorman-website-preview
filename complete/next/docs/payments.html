Put policy before an agent payment.

For agent platform owners: authorize a declared payment intent before your own payment system settles it.

Separate authorization from settlement.

Doorman provides the decision, budget and audit plane for declared non-LLM payment intents. Your application must call it before using your wallet, facilitator or payment service. It does not hold funds or automatically intercept every HTTP 402 response.

  • An organization administrator and the payment-policy API in your deployed environment.
  • A valid traffic key or supported organization session for authorization.
  • A sandbox payment integration that obeys allow, approve_required and block.
  • A stable intent identifier and a designated human approver.
Start with the sandbox

There is no dedicated payment console promised by this guide. The current integration uses the server API, and the policy is disabled by default. An allow response while disabled does not establish an enforced payment policy.

Set the allowance and approval boundary.

An administrator can save the policy using PUT /api/payment-policy. These are illustrative sandbox values, not suggested limits for a production wallet:

{
  "enabled": true,
  "enforcement": "block_with_override",
  "period": "day",
  "capUsd": 25,
  "perPaymentMaxUsd": 5,
  "approvalThresholdUsd": 1,
  "counterpartyAllowlist": ["news.example.com"],
  "requireAllowlist": true
}

Use the authenticated administrator workflow and CSRF protection. This allowance is separate from model inference budgets. Per-payment ceilings and payee restrictions can block even when the period allowance has room.

Authorize each intent before paying.

The application calls POST /api/agent-payments/authorize with its traffic key in x-api-key or a supported organization session. This is a declared sandbox intent:

{
  "amountUsd": 2,
  "counterparty": "https://news.example.com/article",
  "protocol": "pay_per_crawl",
  "agentId": "pilot-research-agent",
  "currency": "USD",
  "idempotencyKey": "pilot-article-purchase-001"
}

Keep the same idempotency key for retries of this same intent. Use a new key for a different purchase. If a retry changes the intent under an existing key, expect 409 idempotency_key_conflict and resolve the mismatch. Record the returned paymentId, decision, reason and approvalState. An HTTP 200 can still mean approve_required; do not equate transport success with payment permission.

Wait for the actual decision.

DecisionApplication behavior
allowProceed only within the authorized intent and your payment system’s own checks.
approve_requiredDo not settle. Wait for an administrator to review the pending item.
blockRefuse settlement and surface the reason.

An administrator reads GET /api/agent-payments/approvals and uses POST /api/agent-payments/approvals/:paymentId/approve or /deny. The agent rechecks authorization with the same idempotency key to read the current state. Doorman records the decision; your payment system remains responsible for actual settlement and duplicate-payment protection.

Prove the gate in your integration.

  1. Test an allowed intent, an approval hold, an over-ceiling refusal and an unlisted counterparty.
  2. Confirm the payment adapter never settles a pending, blocked or failed authorization.
  3. Retry the same intent and verify the audit identifier/state; separately verify that your settlement adapter does not double-charge.
  4. Review the period summary and your payment system’s records together. Authorized amounts are not independent proof of completed settlement.

Malformed amounts and authorization faults are blocked. That refusal should stay visible to the caller rather than being retried as a new purchase.

Resolve the intent before trying again.

For a hold, use the approval queue; changing the idempotency key is not an approval workaround. For a blocked payee or ceiling, have the policy owner review the request. For an ambiguous payment-provider result, reconcile in that payment system before another settlement attempt. Keep wallet keys and payment credentials out of Doorman request bodies.
