Connect agents to governed tools.

For agent developers: use the Model Context Protocol (MCP) to read Doorman context or proxy a registered tool server.

Choose the MCP job.

GoalEndpointWhat it does
Let an agent inspect its allowance and routePOST /mcp/agentRead Doorman metadata scoped to the traffic key.
Govern access to a third-party MCP server/mcp/:serverIdProxy calls to an organization-registered upstream.

Both use a valid Doorman dk_* traffic key. For the proxy path, an administrator must register the upstream and its server-side authentication first. These endpoints do not use the browser’s session or a dak_* control token.

Make one read-only tool call.

Supply your approved gateway origin and traffic key locally. The stateless agent endpoint accepts a direct tools/call request with both required Accept types.

curl --fail --show-error \
  "https://gateway.example.com/mcp/agent" \
  -H "x-api-key: $DOORMAN_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  --data '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/call",
    "params": { "name": "get_budget_status", "arguments": {} }
  }'

Expected result: an MCP response containing the budgets applicable to that caller, or an explicit tool error. It does not spend the agent’s model-request allowance. A key without an owner can read organization aggregates but has no personal last-route result.

Ask a useful operational question.

ToolAgent question
get_budget_statusWhich allowances apply before I start?
explain_last_route / list_recent_routesWhich models handled my recent work?
get_task_costWhat has this task cost so far?
get_spend / get_savingsWhat do the recorded organization totals show?
list_models_for_tierWhich anchor models and estimated rates are available?

Treat costs as estimates and empty personal results as missing scope or data. These tools read context; they do not change routing policy or authorize an otherwise forbidden tool.

Register the upstream before connecting.

  1. In your own organization, register the MCP server’s approved HTTPS URL and server-side auth reference. Keep the upstream secret in the provider vault.
  2. Set server and per-key request limits as appropriate, then copy the returned server ID.
  3. Configure the client to use https://gateway.example.com/mcp/SERVER_ID with its traffic key. Preserve the original MCP configuration.
  4. Make a harmless tools/list or permitted read call. Inspect the recorded server, tool, verdict and result.

The registry uses /api/orgs/:id/mcp-servers; writes require an organization administrator and the authenticated session procedure. A minimal no-auth upstream body is:

{
  "name": "Pilot knowledge tools",
  "url": "https://tools.example.com/mcp",
  "authType": "none",
  "active": true
}

Use the authentication mode your real upstream requires. Doorman resolves upstream credentials server-side; the caller’s traffic key is not the upstream secret.

Test the boundary you intend to enforce.

Start access controls in monitor mode. Use the server/key simulator and tool-policy dry run, then check a real allowed call before enforcement. Review allow/deny, rate limits and tool arguments as separate controls. An issuer value in configuration is only meaningful when the deployment supplies verified claims.

Coverage is at the call boundary

The proxy can govern an MCP call and record hashed arguments. Forwarded server-sent event (SSE) content is not a promise of per-event inspection. A direct upstream connection bypasses this proxy path.

Use the error to find the layer.

Check expired/revoked key on 401, access policy on 403, same-organization server ID on 404, and Retry-After on 429. For an upstream error, verify the registered URL, authentication and provider reachability. Restore the saved client configuration only through your approved recovery process.
