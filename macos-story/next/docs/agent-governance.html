For security and agent owners: test a tool boundary, assign autonomy, and review the exact action before release.

Map the action to its visible path.

Name the agent owner, its traffic key, tools and destinations. Identify whether Doorman sees the model’s tool-call response, a governed MCP call or another supported proxy path. Record whether the client streams. A policy cannot govern an action that never crosses the configured path.

QuestionControl
May this key reach this tool server?MCP server/key access controls.
May this principal call this tool with these arguments?Tool policy and conditions.
May the agent act without a person?Autonomy tier and the applicable approval queue.
May it contact this destination?Agent egress policy on supported visible traffic.
May it spend money outside inference?The separately integrated payment authorization API.

Create one policy in shadow.

  1. Open Guardrails → Agents → Tool policies in your own console and create a narrowly named policy.
  2. Select the intended user/key principal, a tool pattern and any required argument conditions.
  3. Choose permit or deny and start in shadow mode. Test an intended match and a legitimate non-match with the dry-run control.
  4. Inspect which policy matched and why, then run a harmless real pilot action and compare the recorded finding.

A pattern such as *delete* matches tool names; it does not understand every possible destructive action. Conditions inspect the supplied tool arguments, and all conditions must match. Deny overrides permit where applicable.

Choose when a person joins the flow.

TierWhat to verify
read_onlyRead tools pass; mutating or unknown tools are candidates for a hold.
proposeThe agent can prepare work while write actions wait for review.
auto_executeThe tier permits action; other tool and drift policies still apply.

Start with monitor behavior and inspect the findings. Name patterns for tools the heuristic classifies incorrectly. Intent-drift checks compare declared task context with the action; they are a signal to review, not proof the agent understood the full business goal.

When the pilot findings are useful, an administrator can enable the supported hold behavior for the chosen workflow.

Review an exact held action.

  1. Open the appropriate queue: a held tool call and a held agent run are separate review objects.
  2. Read the agent, tool, reason and available arguments/context. Check what the approval will release.
  3. Approve or deny that item through the supported administrator action.
  4. Have the agent retry through its supported flow and confirm the resulting action and audit state.

Tool approval is bound to the action’s hold key. It does not grant unrelated actions or override an explicit tool denial. Current tool approvals can remain effective for that matching action until denied; do not describe them as a guaranteed single-use token.

Test the full boundary before enforcement.

  • A permitted read completes with the expected verdict.
  • The targeted write produces a shadow finding, then a deliberate hold on the supported enforcement path.
  • A pending or denied approval does not release the held action.
  • An approved action resumes only as the application’s retry flow supports.
  • The same check is repeated for the real provider, format and streaming mode.
Streaming needs its own proof

Use the validated non-streaming path for the initial enforcement pilot. Do not infer stream blocking from a saved policy or a shadow finding; transport coverage and hold behavior depend on the deployed relay.

Keep a useful path back to work.

For a false match, correct the tool pattern or condition and retest the saved policy. For an approval that should no longer apply, deny it through the queue. For a failed queue read, the held action should remain held. Notify the owner with the record identifier, not a pasted secret or full private prompt.
