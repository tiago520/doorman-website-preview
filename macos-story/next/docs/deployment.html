Start a Mac rollout with the app.

Request native preview access for an evaluation of sign-in, tool detection and diagnostics. Automatic configuration and routing remain in development. Plan future company self-service or MDM distribution with IT after agreeing the supported package and permissions; public signed and production MDM installers are not published yet.

Prepare managed Mac installation ↗

Define the pilot before installing.

Choose one owner, a small set of supported clients, one gateway origin and a review date. Record the current endpoint settings and agree what success means: attributable requests, acceptable responses, expected policy outcomes and a tested recovery path.

  • Administrator access to the intended organization and its provider credentials.
  • An approved gateway build or hosted environment, allowed models and a pilot allowance.
  • Named owners for DNS/TLS, network egress, data retention and incident response.
  • For managed Macs: the supported native evaluation build and your IT deployment policy.

For a LiteLLM coexistence pilot, agree which router handles model choice and inspect each hop. If LiteLLM multiplexes people through one shared credential, Doorman can govern that organization path and slice recorded cost tags; it cannot reconstruct per-user identity. Keep separately imported LiteLLM spend distinct from gateway-metered traffic.

A private gateway still sends requests to the configured upstream. A fully isolated deployment needs reachable local model services; putting the gateway in a VPC alone does not keep every prompt in that VPC.

Prove one client before the fleet.

  1. Have the operator confirm that the deployed service is healthy and the organization/provider setup is complete.
  2. Use the matching client recipe ↗ with an issued traffic key; save the original settings.
  3. Send a recognizable non-sensitive request. Open Requests in your own console and match its time, identity and outcome.
  4. Repeat with a representative task, including your normal response format and streaming behavior.
curl --fail --show-error \
  "https://gateway.example.com/healthz"

Replace the example origin with the approved environment. A successful health response checks the service; the recorded client request proves the traffic path.

Inspect sample tool coverage ↗

Keep an acceptance record.

  • Gateway release and region; client versions and supported connection methods.
  • One request ID per tested path, expected identity, model and policy result.
  • Who can administer budgets, keys and policies; how users receive help.
  • Storage/retention decisions and a successful backup-restore drill for customer-operated service.
  • A pause or rollback test, the owner who performed it, and the verification afterward.
Customer-operated installation

Use the deployment package supplied for your evaluation. This guide does not substitute an unverified installer command or a historical roadmap for a released distribution.

Recover before expanding.

Restore the saved client configuration if the pilot path fails, following your network policy. For managed devices, ask the operator to apply the approved recovery action. Keep the failure time and request ID, then verify a successful request after recovery.
