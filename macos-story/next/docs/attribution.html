Follow a task from request to PR.

For developers and engineering leads: connect individual calls to the work that produced them.

Start from a verified request.

You need a configured client, a recognizable test task and access to its Requests view. Confirm the key owner and recorded application before grouping work. Decide whether one task means a user request, a background run or a branch; use that definition consistently.

SignalMeaningLimit
Traffic key and recorded ownerWho the gateway authenticated for this path.A shared service credential cannot identify every human behind it.
Explicit task IDThe client deliberately grouped these requests.It is client-supplied attribution, not proof of authorization.
Repository and branchContext can group related coding work.A branch can contain multiple tasks or lack a PR number.

Give a multi-step run one identifier.

On a client path that forwards the task header, use the same x-doorman-task value across the requests that belong together. The Anthropic-compatible example below deliberately uses a small response and your own allowed model.

curl --fail --show-error \
  "https://gateway.example.com/anthropic/v1/messages" \
  -H "x-api-key: $DOORMAN_API_KEY" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -H "x-doorman-task: pilot-connection-check" \
  --data '{
    "model": "YOUR_ALLOWED_MODEL",
    "max_tokens": 32,
    "messages": [
      { "role": "user", "content": "Reply with: connection check" }
    ]
  }'

Replace the origin and model, and supply the key locally. This sends a real model request and can incur usage. Start a new task ID for different work; reusing one generic ID would merge unrelated runs.

Read the task rollup and its source.

Open Tasks in your own console and find the identifier. Compare the request count and timeline with your test. A header-sourced task is explicit grouping; a branch-sourced task is inferred from repository/branch context. Requests with neither remain ungrouped.

FieldHow to read it
Steps and errorsRecorded requests and error steps in the selected task.
Cost and model mixMeasured estimates by model, not a productivity score.
Wall-clock durationFirst-to-last request span; not active developer time.
DCUA comparison unit calculated from cost and the returned reference value; not an extra billable charge.

Check the branch before attaching a PR.

In Pull Requests, confirm repository, branch and owner before associating a PR number. Supported coding context can infer the branch; an explicit attachment supplies the PR number where needed. Review open/merged/closed/abandoned status independently from a model-quality score.

For shared branches, explain what the grouping includes before using the total in a project report. Missing repository or PR metadata should remain visible. A client-supplied repository tag is useful for attribution; it is not a verified security boundary.

Export a report you can reconcile.

  1. Use a fixed time window and the same self/organization scope for every comparison.
  2. Match the task’s request count, cost and model mix to its detail records.
  3. Retain the grouping source, missing attribution and any timeline truncation.
  4. Use the supported Control API for scheduled metadata exports; follow pagination and keep the report window.

Correct the grouping at its source.

If a task is absent, confirm the client forwards its header and sends traffic through the expected path. If unrelated work is combined, use distinct IDs on future runs and explain the affected reporting interval. If a PR attachment is wrong, correct it through the supported console workflow and recheck the underlying branch. Do not invent missing historic identity.
