On a Mac? Start here.

The app gives you one place to review sign-in, detected tools and local diagnostics. Request the supported preview for macOS 14 or later, follow its supplied installation instructions and continue with Google in your browser.

  1. Return to the app and confirm the email you intend to use.
  2. Review the supplied connection and permission instructions for your build.
  3. Open View apps and run Check this Mac to see what is ready and what remains to be set up.

The current preview provides account setup and diagnostics; automatic tool configuration and routing are still being built. Use the guide for the evaluation path and the IT maintenance checklist.

Already have a gateway and key? Use manual setup ↓

Advanced: prepare a direct API connection.

You need access to the intended workspace, its gateway origin and an issued Doorman key. Ask the administrator to confirm provider access and an allowed model. Creating an account alone does not connect a provider or activate an allowance.

  • New to Doorman? Create your account.
  • Joining a team? Open its existing console.
  • Operating your own gateway? Prepare the deployment first.
Keep secrets on your machine.

These guides never need your key. Substitute it locally using your approved credential workflow, and save the previous client settings before making changes.

Choose your client’s connection recipe.

Change one client first. Keep the previous settings, and use the matching recipe rather than applying every example.

Claude Code and compatible Anthropic clients

Set the gateway’s Anthropic-compatible base path. Apply these variables in the shell that launches your client.

export ANTHROPIC_BASE_URL="https://gateway.example.com/anthropic"
export ANTHROPIC_API_KEY="YOUR_DOORMAN_KEY"

OpenAI-compatible API clients

Use the OpenAI-compatible path in a client that supports a custom base URL. A setting for one SDK does not automatically configure every desktop app.

export OPENAI_BASE_URL="https://gateway.example.com/openai/v1"
export OPENAI_API_KEY="YOUR_DOORMAN_KEY"

Codex CLI

Codex uses a custom provider entry in ~/.codex/config.toml; the generic base-URL variable above is not a substitute. Preserve your existing allowed model setting and other configuration, then add or update this provider:

model_provider = "doorman"

[model_providers.doorman]
name = "Doorman"
base_url = "https://gateway.example.com/openai/v1"
env_key = "DOORMAN_API_KEY"
wire_api = "responses"

Supply DOORMAN_API_KEY through your approved local credential workflow before starting Codex. Use your issued Doorman key, not a dummy value. GUI applications may not inherit shell variables; confirm their effective configuration separately.

Send a small, non-sensitive request.

Launch the configured client and ask “Reply with: connection check” using a model allowed by your organization. Keep the test easy to recognize in the request log.

Expected result

The client receives a response, and a corresponding record appears in your Doorman console. A response alone does not prove it went through the gateway.

Verify the request record step by step ↗

If the first request fails.

For a 401, check the issued key and effective client configuration. For a policy refusal, read the reason and ask the allowance or policy owner. For an upstream failure, keep the timestamp and request identifier before retrying. Restore your saved client settings through the approved recovery path if you need to pause the pilot.

Choose the next control deliberately.

Inspect what was recorded before expanding. Then choose routing policy, budget behavior, or data protection based on the job you need to solve.

  • Give the next tool an appropriately scoped key.
  • Set up routing and understand observe mode.
  • Set and verify the pilot allowance.
  • Test what leaves the gateway.
  • Expand a verified client into a team pilot.
