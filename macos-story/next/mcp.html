Before you start

Know where MCP governance applies.

Keep tool access, peer-agent calls and read-only usage questions distinct.

Does this govern every MCP client automatically?

No. The client must use the registered Doorman proxy path with an appropriate key. Unregistered direct tool traffic is outside that path.

What happens when one agent calls another?

Register a peer agent, then send its A2A calls through Doorman’s /a2a/:agentId path with an appropriate virtual key. Apply peer and key access rules and rate limits. The RPC audit records outcomes, latency and captured task state; MCP & A2A activity shows registered peers and call summaries. Calls made directly to the peer are outside this path.

An administrator can inspect the peer’s public Agent Card to review its advertised skills before registration. This is a requested lookup, not automatic discovery or proof that a skill is authorized. Per-task A2A cost metering is not yet available; streamed task events pass through after the call-boundary checks.

Is every streamed event inspected?

The MCP proxy governs the call boundary and pipes streaming responses through. Do not assume per-event inspection or enforcement.

Does the agent-facing MCP server expose prompts?

Its route and task introspection tools return scoped metadata and estimated costs rather than prompt content. Use the specific endpoint’s access contract when configuring service keys.

Can this govern a provider-hosted agent loop?

Managed agents require a separate call-boundary policy. Doorman can assess a supported visible invocation and capture returned usage, but cannot inspect or stop hidden provider-internal steps mid-run. Review managed-agent boundaries ↗

Where do paid tool calls fit?

The advanced payment-policy API evaluates declared payment intents and records decisions or approvals. Your agent must integrate it before using its own payment provider; Doorman does not move funds. Read declared payment policy ↗
