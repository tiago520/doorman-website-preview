Evaluate a model before changing routes.

For engineering and ML owners: turn a representative workload into a reviewable adoption decision.

Define the decision and the dataset.

Name the workload, current model and one candidate. Write the acceptance criteria before running comparisons: the response must satisfy your task, preserve required formats and tools, and meet your cost/latency constraints. You need an administrator, the evaluation service in your environment, provider access and permission to use the selected data.

ModeWhat it provesUpstream use
Route previewThe configured routing decision for a supplied request.No model call; does not simulate runtime budget enforcement.
Dry evaluation planWhich dataset and candidates a run would use.No live comparison evidence.
Replay/live comparisonHow candidates respond to selected work.Provider and judge usage may incur charges.
Human calibrationWhether the rubric/judge agrees with reviewed labels.Depends on the chosen review process.

Use non-sensitive pilot examples or the approved retained/tokenized dataset path. Zero retention and missing captured content can limit the comparisons available.

Create and inspect a bounded dataset.

The administrative dataset API is POST /api/evals/datasets. In a deployment with this service, the authenticated administrator session procedure can create a dataset with a body like:

{
  "name": "Pilot support answers",
  "source": "traffic",
  "piiMode": "tokenized",
  "filter": { "app": "pilot-support" }
}

Replace the app filter with the exact value recorded by your workload. Creating the dataset does not populate it. Refresh using POST /api/evals/datasets/:datasetId/refresh, then inspect its items and curation result. Tokenized curation requires configured tokenization; a refusal is a setup issue, not an empty successful run.

The sample Experiments screen may not expose every creation action. Use the supported authenticated admin workflow for your release; do not substitute a traffic key for admin authorization.

Review a plan, then authorize live usage.

Create a run with POST /api/evals/runs. This example is a plan only: replace the dataset ID and model identifiers with values from your environment.

{
  "datasetId": 42,
  "kind": "model_swap",
  "candidates": ["YOUR_CANDIDATE_MODEL"],
  "baseline": "YOUR_BASELINE_MODEL",
  "live": false
}

Inspect the planned work before an administrator deliberately launches the live comparison with an agreed usage allowance. Read the deployment’s supported options and worker state. A queued or planning row is not a completed experiment.

Read evidence before the recommendation.

  1. Check dataset size, workload coverage and missing/skipped items.
  2. Compare candidate and baseline on the same criteria; inspect failures and response-format differences.
  3. Review human labels and calibration before relying on a judge’s score. Keep uncalibrated or insufficient results visible.
  4. Read cost and latency beside quality; do not extrapolate an unrepresentative sample to all work.
  5. Save the run and rubric versions with the decision.

Adopt in a narrow slice.

If the evidence supports the candidate, change the relevant routing policy in your own environment and repeat a representative task. Check the actual selected model, outcome and quality evidence. Compare like-for-like windows. If the gate says unknown or insufficient, collect the missing evidence rather than relabeling it as a pass.

Cancel or restore with context.

For a failed run, inspect its error class and worker/provider availability before retrying. The supported run cancellation route is POST /api/evals/runs/:runId/cancel; cancellation does not refund provider usage already incurred. Restore the previous routing policy if the pilot regresses, and keep the failed evidence for review.
