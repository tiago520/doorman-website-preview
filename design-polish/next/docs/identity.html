Connect identity without losing access.

For organization and identity administrators: test single sign-on (SSO), provision a pilot group, and verify offboarding.

Keep an administrator recovery path.

Before changing identity settings, confirm your organization, an identity provider (IdP) test application, a pilot user and an independent administrator recovery path. Record the current sign-in method. Use the capability flags returned by the environment for login configuration, provisioning and enforcement; these are separate permissions.

One successful login comes first

Test a second browser session before requiring SSO for the organization. Do not close the working administrator session while checking the pilot.

Configure and test the login path.

  1. Open Organization → Identity in your own console. Read the returned login/provisioning/enforcement availability.
  2. Copy the service-provider identifiers and callback values from that environment into the IdP. Enter the matching issuer, certificate or supported configuration in Doorman.
  3. Assign only the pilot user at first. Start a new private browser session and sign in through the configured path.
  4. Confirm the resulting organization, email and role. A successful IdP login does not by itself prove the user joined the right tenant.

The SAML configuration surface is /api/orgs/:id/saml-config. Use its returned entitlement flags and the deployment’s actual callback values. Never reuse another workspace’s identifiers.

Connect SCIM with an organization token.

SCIM (System for Cross-domain Identity Management) lets your identity provider provision users and groups. When provisioning is enabled for the deployment, use an organization-scoped SCIM token and the base URL https://gateway.example.com/scim/v2. The operator controls the SCIM_WRITES_ENABLED gate. Begin with reads and a small test group before activating writes.

curl --fail --show-error \
  -H "Authorization: Bearer $DOORMAN_SCIM_TOKEN" \
  "https://gateway.example.com/scim/v2/Users"

Replace the origin and supply the token locally. Confirm the returned users belong to the intended organization. A general control token or model-traffic key is not a SCIM credential.

Use the implemented provisioning operations.

OperationCurrent behavior to validate
Users: list, read, createOrganization-scoped; create requires the write gate and an organization token.
Users: PATCH/PUT activeDeactivate/reactivate is supported with writes enabled; other attribute updates can return 501.
Groups: list, read, createGroups map to departments; create requires writes enabled.
Groups: PATCH membership/nameSupported add/remove membership and rename operations; test your IdP’s exact payload.
Delete user; PUT/DELETE groupNot a complete deletion workflow. Use the supported deactivation path and review the response.

Do not enable every operation offered by the IdP wizard just because the connection test passes. A 501 identifies an unsupported operation; retrying it will not provision the user.

Test access removal as well as entry.

  1. Provision or assign a pilot identity; confirm tenant, role and department.
  2. Deactivate the pilot through the supported active:false operation. Confirm sign-in and the affected credentials no longer work.
  3. Inspect the offboarding audit event and revocation result.
  4. Reactivate deliberately. Expect a new sign-in and re-enrollment where keys were revoked; reactivation must not resurrect old sessions.

Check group policy effects separately from identity creation. Group removal does not imply every role was demoted; review administrative roles explicitly.

Recover from a mapping mistake.

Use the preserved administrator path to correct the IdP assignment, tenant configuration or group mapping. Keep SSO enforcement off for the pilot until the repeated login/offboarding checks pass. Rotate an exposed SCIM token and retest its intended organization scope.
