Give each integration the right key.

For developers and administrators: separate provider credentials, model traffic and control automation.

Choose the credential by its job.

CredentialUsed byPurpose
Provider credentialGateway provider vaultAuthorize upstream model access.
Doorman traffic key · dk_*AI client or governed MCP clientIdentify and constrain model/tool traffic.
Control token · dak_*Reporting or administration scriptCall the scoped /api/v1 Control API.

Before you start, confirm your organization, administrator access, the allowed provider/models and a secure place to store the new secret. A traffic key is not an admin session, and a control token is not a provider key.

Issue a key for one workload.

If provider access is not configured, an administrator first opens Keys → Provider vault and adds the organization’s approved provider credential. This is bring your own key (BYOK): choose the provider, a useful label and the pool weight, then use Vault it. Store the original through your organization’s secret workflow; the vault does not display it again. Inspect provider health, then verify access with the workload key below. Subscription seats have a separate registration and quota lifecycle; do not treat a consumer subscription as an interchangeable API key.

  1. Open Keys in your own organization. Choose an owner or service workload and a name that explains its purpose.
  2. Apply the supported model, budget, expiry and network restrictions appropriate to that tool. Check that the restrictions still permit the pilot request.
  3. Store the secret when shown. Configure the matching client endpoint and traffic key together.
  4. Send one small request and confirm the key/owner in Requests before giving it to another tool.

For short agent runs, an ephemeral child key can tighten the parent’s limits. Its parent and its own expiry/revocation state both matter; do not assume a child can widen its parent’s access.

Start automation with a read.

In API tokens, mint a purpose-named token with only the scopes the script needs. This example needs read:org and read:stats. Store the one-time secret in your approved secret manager and supply it locally as DOORMAN_CONTROL_TOKEN.

curl --fail --show-error \
  -H "Authorization: Bearer $DOORMAN_CONTROL_TOKEN" \
  "https://gateway.example.com/api/v1/org"

curl --fail --show-error \
  -H "Authorization: Bearer $DOORMAN_CONTROL_TOKEN" \
  "https://gateway.example.com/api/v1/stats/summary?window_hours=24"

Replace the example origin. Confirm org_id and the returned token scopes before reading a report. The summary reports its actual window_hours; retain that with the numbers.

Use the deployed API reference.

Your gateway serves /api/v1/docs and /api/v1/openapi.json. Use those for the routes, scopes and request fields supported by that deployment. Request metadata uses read:requests; activity aggregates use read:analytics. Follow cursors and truncation signals when exporting.

Browser administration and automation differ

The console’s session-protected admin routes use its authenticated session and CSRF protection. A dak_* token grants its documented /api/v1 scopes; it does not authorize every /api admin route.

Use the session for administrative APIs.

Examples outside /api/v1 often use the console’s authenticated session. Prefer the matching control in your own console: it sends the session cookie and protects state-changing requests against cross-site request forgery (CSRF). A dak_* token does not replace that session.

Advanced: make an authenticated preview request
  1. Sign in to your own gateway console and confirm the intended organization. Administrative writes require the appropriate administrator role; some gateway-wide controls also require the operator.
  2. This browser example requires the console and API to share an origin. Open developer tools there, not on the public website or sample console. Use your deployment’s supplied API procedure if they use different origins.
  3. Replace YOUR_ALLOWED_MODEL below. The example reads the local doorman-csrf cookie and sends its value as X-Doorman-CSRF, with the existing session.
  4. Inspect the returned routing preview. This example does not save a policy or call an upstream model.
await (async () => {
  const cookie = document.cookie.split(/;\s*/)
    .find(value => value.startsWith("doorman-csrf="));
  if (!cookie) throw new Error("Sign in again before using this example.");
  const csrf = decodeURIComponent(cookie.slice("doorman-csrf=".length));
  const response = await fetch("/api/route-preview", {
    method: "POST",
    credentials: "same-origin",
    redirect: "error",
    headers: {
      "Content-Type": "application/json",
      "X-Doorman-CSRF": csrf
    },
    body: JSON.stringify({
      provider: "anthropic",
      model: "YOUR_ALLOWED_MODEL",
      prompt: "Reply with: connection check"
    })
  });
  if (!response.ok) throw new Error(`Preview refused: HTTP ${response.status}`);
  return response.json();
})();

Keep session cookies and CSRF values in this browser; do not copy them into tickets or the public website. A successful preview verifies this request’s session handling, not permission for every administrative route. For a 401, sign in to the intended environment again. For a 403, inspect the role, organization, CSRF error or operator requirement before retrying.

For recurring automation, use the scoped /api/v1 Control API where it supports the task. Do not turn a copied browser session into a long-lived service credential.

Verify access and a safe refusal.

  • The token identifies the intended organization and no broader scopes.
  • The intended read succeeds and the response window matches the script’s report.
  • A test using a revoked token is refused. Do this with an expendable pilot token.
  • The application handles access errors without printing the secret or retrying forever.

Rotate with a verified handover.

Issue or rotate using your organization’s supported workflow. Update one consumer, make a successful request, then remove the old credential when the handover is complete. A lost one-time secret must be replaced. For suspected exposure, revoke promptly and inspect the affected key’s activity; do not paste it into support tickets.
