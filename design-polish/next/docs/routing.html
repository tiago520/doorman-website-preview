Change a route. Verify the result.

For platform and engineering owners: preview a representative task, adjust one control and verify the model that actually served it.

Choose the workload and the owner.

Start with a verified client, an allowed model and one repeatable task. Record the current routing settings and the expected response, including tools, structured output and streaming. An administrator manages organization settings; the gateway operator owns controls that affect every organization.

Connect a client first ↗ · Keep a baseline request ↗

Preview before changing a setting.

  1. Open Routing → Route preview in your own console.
  2. Select the request’s actual provider and model. Enter a synthetic example of the task and its recorded app name where relevant.
  3. Read the selected tier, model, reason and cost estimate. Compare a routine task with a demanding one.
  4. Keep the preview beside the original request for the later live check.

The session-authenticated endpoint is POST /api/route-preview. Replace the model and app name in this example with your pilot values:

{
  "provider": "anthropic",
  "model": "YOUR_ALLOWED_MODEL",
  "appName": "pilot-client",
  "prompt": "Write a short explanation of this function.",
  "max_tokens": 128
}

Use the authenticated session procedure for API examples; each endpoint still requires its own role.

A preview is a routing estimate

It makes no upstream model call and creates no real request record. It does not prove answer quality or simulate runtime budget enforcement. The preview uses the signed-in caller’s organization and role; repeat with the actual client key to verify key-specific behavior.

Separate controls by their scope.

ControlUse it forCheck before changing
Org routing modeChoose the configured provider or Doorman model path.Provider credentials, target availability and organization scope.
Observe-only modeClassify and record while preserving the requested model.This is gateway-wide. On a shared gateway, the operator must authorize the change.
Client model allowlist / Blocked modelsConstrain which models the organization may use.Required capabilities and the permitted model for each pilot client.
Confidence gateChoose the fallback when task classification is uncertain.The returned reason and behavior on ambiguous tasks.
Off-peak scheduleApply the supported routing action in defined time windows.Window order, days, timezone and a test at the boundary.

Open Routing → Routing desk to inspect these controls. The tier table shows the current release’s model anchors; it is not a table you edit directly. The operator controls gateway-wide Observe-only mode. It stops routing substitutions; data-protection and other policies keep their own settings.

Set up data protection separately ↗

Change one setting in a pilot.

  1. Agree the intended scope, owner and recovery action. Use a test organization or a documented workload limit where the control supports it.
  2. Save one supported organization setting. Reread the value and record the change time.
  3. Send the same task through the original client and key. This is a real provider request and may incur usage.
  4. Inspect its requested and served model, routing reason, cost, output format and task result.

A requested model that stays unchanged can be correct: observe mode, confidence, capabilities or an explicit choice may preserve it. A different model still needs a useful result. Test the actual provider format and streaming behavior before expanding.

Compare model quality on representative work ↗

Keep the checks together.

EvidencePass condition
ConfigurationThe saved control and its scope match the agreed change.
RequestThe intended client, key and organization produced the record.
RouteThe selected model and reason explain the outcome.
WorkloadRequired tools, format and response quality still work.
LimitsApplicable budgets and other controls behave as intended.

Keep missing prices or quality evidence visible. A dry preview and one successful request are a starting point, not evidence that every workload should change.

Test the pilot allowance ↗

Restore the setting that changed.

If the task regresses, restore the recorded setting through the authorized owner and repeat the request. Use configuration history where the control supports it. A refused global-mode change with operator_required belongs with the gateway operator; repeatedly changing organization settings will not grant that access.

For an unexpected route, check the effective mode, allowed models, active schedule, confidence reason and client configuration before trying another change.
