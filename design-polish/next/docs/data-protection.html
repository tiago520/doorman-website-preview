Check the data that leaves.

For security and application owners: test personal-data handling, outbound rules and response inspection on one verified client path.

Choose the control for the data.

You need an organization administrator, a verified gateway client and synthetic examples you may inspect. Record the current policy, provider format and streaming mode. Use a test organization for initial changes: an organization setting can affect more than one pilot user.

ControlWhat it doesWhat it does not establish
Personal-data tokenizationReplace supported personal information with tokens before sending; restore it in the response.A guarantee that every identifier is recognized.
Data loss prevention (DLP)Match outbound content against configured patterns and alert or block.Redaction through a DLP rule; use tokenization for supported reversible replacement.
Output guardrailInspect model responses and apply supported monitor, redact or block actions.Identical enforcement across every category or transport.
Retention and residencySet the separate rules for stored content and permitted locations.These do not become configured merely because a detector is enabled.

Verify the client path first ↗ · Review data-handling requirements ↗

Test tokenization before enabling it.

  1. Open Guardrails → Data protection → PII tokenization. PII means personally identifiable information.
  2. Inspect the selected pack and its Active entities. Pack names select detector sets; they do not certify compliance.
  3. In Round-trip proof, test a fictional address. Compare Upstream sees with You get back.
  4. Require a successful transformation and restoration before enabling the intended entity set for the pilot.

POST /api/tokenization/test also accepts temporary test settings. This selects email detection for the test without saving the override or calling a model:

{
  "prompt": "Contact pilot@example.com about the test.",
  "config": { "entities": ["email"] }
}

Check ok, entities, byType, upstream and roundTrip. A degraded result or an unchanged address does not prove protection. The test forces its transform on; it does not mean the saved policy is enabled.

After review, enable Tokenization enabled and reread the effective entities. The administrator configuration endpoint is PUT /api/tokenization. Use the authenticated session procedure for API examples; each endpoint still requires its own role.

Start an outbound rule with alerts.

In Data protection → DLP rules, inspect the organization’s rules and alerts. A custom rule uses a regular expression: an exact synthetic marker makes the first test easy to explain.

Test the pattern with POST /api/admin/security/rules/test:

{
  "pattern": "DOORMAN_PILOT_ONLY",
  "sampleText": "Example note: DOORMAN_PILOT_ONLY"
}

Expect one match; repeat with text that omits the marker and expect none. This tests pattern matching only. An administrator can create the pilot rule with POST /api/admin/security/rules:

{
  "name": "Pilot marker",
  "pattern": "DOORMAN_PILOT_ONLY",
  "action": "alert"
}

Use the session procedure if your console does not expose creation. Save the returned rule ID. Send a synthetic client request containing the marker and inspect its alert. The supported DLP actions are alert and block; do not configure redact as a DLP action. Test a deliberate block only after agreeing the affected scope and recovery.

Check the response path separately.

Open Guardrails → Output rail and begin with monitor actions. Use Playground to inspect a synthetic response before changing enforcement. POST /api/guardrails/test accepts a response string and makes no model call.

An administrator sees the policy-based action and the text a user would receive. A member’s test shows detector findings with neutral monitor behavior; it cannot verify the administrator’s enforcement policy. The playground can test a disabled rail, so check the saved enabled state too.

Read enforcesNonStreaming, enforcesStreaming and enforcementScope from the output configuration for your deployment. The current stream path records monitor findings; a non-streaming block result does not prove streamed text will be withheld. Test the exact response format you use.

Inspect sample data-protection controls ↗

Verify an actual application request.

  1. Send one clean and one synthetic matching input through the intended client and key.
  2. Match the request, organization, time and policy result. Review tokenization coverage or the corresponding alert rather than inferring protection from a successful response.
  3. Confirm the intended client outcome: useful restored text, an alert without refusal, or the deliberate policy block.
  4. Repeat with the actual provider, structured fields, tool content and streaming mode your application relies on.

Tokenization and scanner faults can forward the original content. Treat an uninspected or degraded result as a coverage gap. Retention settings and provider data handling remain separate review items.

For retrieved documents, use the retrieved-context guide. For actions the model asks an agent to take, use tool policy and approval controls.

Correct the rule and repeat the test.

For a false positive, keep a synthetic reproduction and restore the previous configuration while the owner reviews the match. A custom DLP pilot rule can be removed with DELETE /api/admin/security/rules/:id; use its saved ID and leave unrelated rules intact. Inspect the current rule list after removal.

For missing findings, check policy enablement, the selected entities, organization and actual request path. An unavailable report is not an empty successful scan. Keep the policy version and the verified request with your acceptance record.
