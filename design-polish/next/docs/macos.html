Set up your Mac. Keep it clear.

A practical guide for your first Mac and the IT team supporting it: get preview access, confirm the account and know where to check next.

Prepare one Mac.

Have a Mac running macOS 14 or later, a Google account accepted by your Doorman environment and an IT contact if the device is managed. The current desktop sign-in flow uses Google; confirm account eligibility before starting.

What you can evaluate today

The development build supports sign-in, account confirmation, app detection and diagnostics. It configures supported shell connections and verifies Claude Code in a fresh default zsh terminal. Existing terminals, custom ZDOTDIR shells, Bash, Codex and Gemini remain outside that verification. A signed customer installer and production MDM package are not published yet.

Request Mac preview access ↗

You will need the supported evaluation build and its installation instructions from Doorman or your IT contact. The website’s approved interface gallery shows design previews with example data; the native capture archive is labeled separately.

Sign in and review this Mac.

  1. Install the supplied preview. Follow the instructions for that exact build, including its background helper. Keep the build version and the installation notes for support.
  2. Open Doorman and choose Sign in. Continue with Google in your browser. Use the account intended for this evaluation.
  3. Confirm the email in the app. On first run, review “Use this account?” and choose Done only when the email is yours. On a later sign-in, the confirmation reads “Use this account”. This confirmation links the Mac to that account.
  4. Review the connection instructions. Read any requested permissions and the supplied explanation of what changes. For a managed Mac, involve IT when a request conflicts with endpoint policy. Account confirmation alone does not prove routing. After configuration, open a fresh default zsh terminal and read the helper’s connection result.
  5. Open View apps, then Check this Mac. Inspect the detected tools and the diagnostic report. Confirm the account and background helper before investigating a tool’s connection.

You now have a familiar place in the menu bar for status and help. Keep using your existing tools while you and the pilot owner review the next supported connection step.

Read status by what it proves.

Use the text beside the Switch and the detail for each app. A detected app or a configured environment variable alone does not prove its requests use the gateway.

For a supported live client path, send one harmless request and match its record in the workspace. Keep enrolled devices, detected tools and verified requests as separate pilot results.

Give IT a repeatable pilot.

Choose a small, representative group and one support owner. Company self-service and mobile device management (MDM) are delivery options to plan with Doorman as the supported package becomes available.

OwnerAgree before expanding
Endpoint ITPackage version, supported macOS versions, signature and notarization review, installation method and a tested removal procedure.
Identity administratorAccepted account, intended workspace and sign-out or offboarding procedure. Confirm desktop sign-in support for your identity setup.

A useful handoff is short: Mac and app version, intended account/workspace, tools tested, diagnostic result, and a request reference for each verified connection. This gives IT a support record and finance a defined scope to review.

Use Apple’s package distribution guidance for the management mechanism. Doorman-specific payloads and permissions must come from the supplied package documentation.

Plan your managed Mac pilot ↗

Keep routine support in one place.

After a build update, an account change or a connection problem, open Doorman and run Check this Mac. It checks the helper, account, detected routing and existing networks without changing connection settings.

SituationNext action
Sign-in is waiting or expiredReturn to the browser flow or start sign-in again. Review the email before confirming; sign out if the account is wrong.
The helper is unavailableOpen Doorman and read the helper message. Have IT confirm the background helper was installed for your login user using the supplied build instructions.
Routing says Not yetCheck the build’s supported connection path. Repeating diagnostics does not enable an unfinished integration.
A check needs attentionRecord the check name and detail. Use Fix when the app recommends it, then run the checks again and inspect the result.
You are updating or leaving the pilotUse the owner’s update or removal procedure. For offboarding, sign out while online and have the administrator confirm the device’s access is retired.

During a gateway outage, the helper retains its last configured route; automatic direct fallback is not implemented. Pause restores settings owned by Doorman for new terminals. Existing terminals keep their environment, and quitting the menu bar app does not undo routing.

A healthy diagnostic report can still contain “Not yet” items. Review the individual checks, then repeat a verified request for any live path you rely on. Share relevant results with support, keeping credentials out of the report.

Advanced: evaluate the native source build.

For authorized developers, use the supported native source with Xcode command line tools and Go on macOS 14+. A local development gateway can request email sign-in instead of Google; follow the instructions for that environment. The build creates an ad-hoc signed build/Doorman.app. Run the helper installation as the login user:

./scripts/build-app.sh
./scripts/install-helper.sh "$PWD/build/Doorman.app"
open build/Doorman.app

This registers the development helper as a per-user LaunchAgent. Use the actual helper for account and diagnostic evaluation; the bundled fixture helper is for example UI states and must not run alongside it.

Optional command-line diagnostics for IT

The native app’s command talks to the same helper. Install its optional link from the source checkout, then run status and diagnostics as the login user:

sudo ./scripts/install-cli.sh "$PWD/build/Doorman.app"
doorman status
doorman doctor
doorman doctor --json

doorman fix retries the app’s supported recovery checks when directed. It is separate from the gateway repository’s command with the same name. The installer preserves an existing unrelated command.

ExitMeaning
0Command completed; doctor has no attention checks. Pending setup may remain.
1The helper did not answer.
2The command arguments need correction.
3Doctor found at least one check needing attention.
4The helper response was unexpected or its local token was refused.

For development cleanup, use the supplied removal procedure. ./scripts/install-helper.sh --uninstall restores settings owned by Doorman before removing the helper’s LaunchAgent; it refuses removal if restoration is incomplete. Quitting the menu bar app alone does not withdraw routing. sudo ./scripts/install-cli.sh --uninstall removes the optional command link. These scripts do not constitute a complete customer uninstall or remove every saved file.

Use a direct client when appropriate.

For an API service or a tool with a configurable endpoint, follow the manual recipe and verify its request independently of native app sign-in.
