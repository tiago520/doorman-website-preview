Doorman guides

Turn a change into reviewable evidence.

For security and platform owners: record what changed, inspect its effect, and share a bounded artifact.

Define the question and the time window.

Choose one investigation or review question: who changed a budget, why an agent action was held, or which controls covered a period. Confirm the organization, administrator role and available retention window. Keep the original request or event identifier and use explicit timestamps with timezone.

ObjectWhat it establishes
Audit eventA recorded actor, action and time.
Configuration versionA captured change and its supported comparison/restore fields.
Evidence packA selected set of available records for a defined review.
Signed AI CloseIntegrity verification of a period document and its explicit report fields.
Trust snapshot/share linkAn approved snapshot visible to its authorized recipient.

A report or signature is not a certification, legal conclusion or independent measurement of every claim.

Find the event behind the result.

  1. Open Audit log and set a window around the request or administrator action.
  2. Filter by action and search the available actor/detail text. Use the date controls to narrow a busy organization.
  3. Open Inspect change where before/after values exist. Compare them with the expected setting and scope.
  4. Export the selected evidence when supported, retaining its filters and any truncation or unavailable-data notice.

Inspect the sample audit log ↗

An empty filtered list can mean no matching event, the wrong scope/window or unavailable retained data. Resolve that distinction before reporting “no changes.”

Compare before restoring.

Open Configuration history and compare the relevant versions. Read the changed keys, actor, source and stated impact. A restore is an administrative mutation; save the current version reference and assess who will be affected before confirming it.

Restore creates a new version

The supported restore workflow reapplies the selected configuration and records a new forward version. It preserves the earlier history instead of deleting the change you are investigating.

Verify the setting and the workload.

  1. After a restore or policy update, reread the current setting and new version.
  2. Find the corresponding audit event and confirm the intended actor/scope.
  3. Run a representative non-sensitive request or policy test. Check the client outcome as well as the console state.
  4. If the result is wrong, use the saved version reference and the approved recovery process; do not keep restoring blindly.

Verify a request after the change ↗

Share only the artifact needed.

Generate the evidence pack or trust snapshot for the agreed period and audience. Review its contents, missing data and retention limitations before sharing. Use supported expiring access links for the intended recipient, and revoke them when no longer needed.

For a financial period record, use the AI Close guide to generate the document and verify its signature. Signature success checks the signed document; quality remains measured only where the report says the evidence qualifies.

Keep gaps explicit and repair the source.

If a record is missing, confirm filters, organization, role and retention. If a configuration restore fails, inspect the error and current state before another write. If a shared link is too broad or exposed, revoke it and issue a reviewed replacement. Preserve an incident note with the window, affected record IDs and the checks performed.
